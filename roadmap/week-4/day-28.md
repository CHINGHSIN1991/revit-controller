# Day 28 · 使用者試用、M3 驗收

> 本文件依計畫推估，開始前請依 Day 21 回顧結果修訂。

## 今日目標

請一位真實使用者（實際做碰撞檢討的工程師）在 Revit 中試用完整流程，收集回饋。完成 M3 驗收清單，做一次回顧，並讀懂第五週要做什麼。

## 你會學到

- 可用性測試的進行方式：給任務、觀察、不引導
- 怎麼把觀察到的問題分類成「本週修」與「排入之後」
- 怎麼用固定的清單做里程碑驗收

試用前的說明只講三件事：這是什麼、今天要請你做幾個任務、我們測的是軟體不是你。**不要示範操作。**

## Step 2. 任務腳本

依序給使用者，每個任務只唸任務描述，不提示按鈕位置：

| # | 任務描述（唸給使用者） | 對應功能 | 預期時間 |
| --- | --- | --- | --- |
| 1 | 「請找出 3F 所有還沒處理的碰撞。」 | Pane 篩選（Day 24） | 2 分鐘 |
| 2 | 「挑一筆 AI 判定為真碰撞的，去模型裡看看它在哪。」 | 點選跳視圖（Day 25） | 3 分鐘 |
| 3 | 「你同意 AI 的判斷嗎？請照你的判斷處理這一筆。」 | 接受或改判（Day 25） | 3 分鐘 |
| 4 | 「找一筆 AI 說可以接受的，確認你是否也這樣認為。」 | 判讀理由的可讀性 | 3 分鐘 |
| 5 | 「請 AI 幫你只列出風管對梁的碰撞。」 | Pane 對話（Day 26） | 3 分鐘 |
| 6 | 「AI 還在跑的時候，請讓它停下來。」 | 中斷（Day 26） | 1 分鐘 |
| 7 | 「把剩下需要處理的碰撞匯出給結構技師。」 | 匯出（Day 25） | 3 分鐘 |

使用者卡住超過預期時間的兩倍，才可以給一個最小的提示，並在紀錄表上標記「有提示」。

## Step 3. 觀察紀錄表

每個任務一列：

| # | 完成？ | 用時 | 有提示？ | 卡在哪裡 | 使用者說了什麼（原話） | 嚴重度 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | | | | | | |
| 2 | | | | | | |
| … | | | | | | |

嚴重度：

| 等級 | 定義 | 處理 |
| --- | --- | --- |
| 阻斷 | 無法完成任務 | 今天修，或列為 M3 未通過項目 |
| 重大 | 完成了但很困難，或做錯了自己不知道 | 列入 Week 5 前處理 |
| 輕微 | 有點不順，但不影響結果 | 列入技術債 |

試用結束後問三個問題：

1. 哪一步最讓你困惑？
2. AI 的判讀理由，你會相信到什麼程度？
3. 如果明天要用在真實專案，你最希望先改哪一點？

另外特別記錄：**使用者有沒有不看就按「接受」**（Day 25 的常見問題）。這關係到 Week 5 核准機制的設計。

## 第五週預覽

前四週的平台都是唯讀的（AI 只寫判讀結果，不改模型）。第五週開始讓 AI 提出並執行修正，因此安全與核准機制是重點：

| 目標 | 牽涉的層 |
| --- | --- |
| 定義可自動修正的類型與 `propose_fix` 的格式 | Core、領域知識（MEP 管線幾何） |
| Dry-run：在 `TransactionGroup` 中試做、檢查、rollback | Add-in（`TransactionGroup`、`IFailuresPreprocessor`） |
| 人工核准後執行 `apply_fix`，可整組回復 | Add-in + Sidecar + Pane（核准畫面） |
| ACC Issues 連接器：認證、匯出、雙向同步 | Sidecar（APS OAuth、Issues API） |
| 安全性與異常情境檢查 | 全部（含 prompt injection 的完整威脅分析） |
| v1 發布 | 安裝程式、文件 |

詳細內容見 [week-5/README.md](../week-5/README.md)。

## Week 5 前要先想好的兩件事

1. **核准畫面放哪裡？** Day 31 的核准可以在 Pane 中確認，也可以交給 harness 的權限機制。今天試用中觀察到的「不看就接受」行為，是設計核准畫面的重要依據。
2. **客戶有沒有在用 ACC？** Day 32 要註冊 APS 應用程式並連到客戶專案。如果客戶沒有使用 ACC（SPEC §8.2），要先決定 Day 32 – 33 改做什麼。
